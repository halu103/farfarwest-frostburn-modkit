# Five-to-eight-player mission and Joker investigation

Update: official v1.2.3 implements two adapters based on the current CL2852 assets.
The missile issue is an unhandled 5+ setup switch producing zero timing,
while the success threshold is already four levers. Joker retention shadows
the game's new native reconnect backup and feeds its replicated restore path.
See [current implementation and validation](GAMEPLAY_FIXES.md). The notes below
are historical evidence for the September report; neither adapter has yet been
validated in a real multiplayer run.

Historical packages: v1.2.2 expands room capacity and session UI but only targets game 0.2.0.20. The earlier v1.2.3 legacy-runtime test targets game 0.3.0.7, retains the old capacity/Invite behavior and adds read-only evidence, but **does not** change objective logic or restore Joker data. It is distinct from official v1.2.3, which includes the adapters above. The official October update moved matchmaking to EOS, added native Joker restoration for disconnect/reconnect, and changed missile progression. The earlier v1.2.3 Joker snapshots from a 0.3.0.0 single-host run were `?/?/?/?` and cannot validate restoration. Do not advertise either issue as runtime-verified until a controlled multiplayer test passes.

The development Lua source now records read-only, bounded `JokerSnapshot` lines when PlayerState/Joker counts change and `MissionSnapshot` lines when the TNT missile objective is present with at least four players. After discovering the missile actor, it checks for changed lever state every 500 ms, including the transition from five to four players. The mission line includes the launcher's lever count, how many `BP_Lever.isPulled` flags are true, the TNT requirement/progress, and the blown flag. `MissionEvent` lines trace the game's own lever-enable and ignition functions. PlayerState objects are labelled `p1`, `p2`, etc. rather than by Steam name. Each `pN` has four collection counts in order: character Jokers / item Jokers / runtime Jokers / hero Jokers; `?` means the property could not be read. It does not give back Jokers, complete an objective, change saves, or alter the game installation by itself. These diagnostics are not in the published v1.2.2 package.

The reported case was the **TNT missile objective** during the 01:10–01:41 (Asia/Saigon) five-player Jungle run on 2026-09-27. The players say all four levers were held simultaneously with five connected players and the objective did not activate; after one guest deliberately used Leave/Back, four connected players used the same four levers and it activated. That guest then rejoined without their Jokers; the remaining players kept theirs. The existing v1.2.2 logs establish the player-count transitions and objective level, but do not contain lever states or Joker counts.

The developer's [September 19 devlog](https://steamcommunity.com/app/3124540/announcements/) described restoring found Jokers after a disconnected player reconnects as a work-in-progress feature. The historical report occurred on patch 0.2.0.20; the installed game is now 0.3.0.7, whose October notes describe a native reconnect save path. The reported guest deliberately selected Leave/Back rather than suffering an unexpected disconnect, so neither announcement proves that voluntary exit restores Jokers. It also does not prove whether the mod caused the historical loss.

For a controlled test after everyone is ready to play:

1. Compare the TNT missile with four players and with five players in separate runs. In each run, record how many levers exist, how many are simultaneously active, and whether ignition starts. Do not remove a player from an active run to make the objective work. The 500 ms snapshots can miss a shorter lever pulse, so a missing `4/4` line alone is inconclusive. Do not upload screenshots containing room codes or Steam IDs publicly.
2. Do **not** ask a guest with valuable Jokers to use Leave/Back just to test this. If the group elects to test with disposable Jokers, record that guest's visible Joker count before Leave/Back and after rejoining, plus one staying player's count as a control. A four-player unmodded control run can help separate the game's voluntary-leave behavior from the eight-player mod. Host departure is a separate case and cannot be used to test guest restoration because it closes the room.
3. Keep the game's and UE4SS's logs. On the host they are normally `C:\Users\<you>\AppData\Local\FarFarWest\Saved\Logs\FarFarWest.log` and `<game>\FarFarWest\Binaries\Win64\ue4ss\UE4SS.log`. Share only the time range around the event, and redact Steam IDs, player names, lobby/session codes, and network addresses.
4. In UE4SS.log, compare `ObservedPlayers`, `JokerSnapshot`, and `MissionSnapshot` at the same time. A rejoining guest normally has a **new** PlayerState object and therefore a new `pN` label. The host must correlate the departure/rejoin timing; the added log intentionally does not contain Steam IDs. A nonzero host-side Joker count with a blank UI points toward presentation/cache; a new guest state with zero Jokers points toward missing reconnect restoration. Neither alone proves whether a save was changed.

The missile asset exposes both a player array and lever state. We extracted its cooked UE5.8 package read-only, but the available converter did not reliably decode the mission's Blueprint bytecode; several function exports had implausible fields and the main event graph remained raw. Names alone do not prove that the blocking condition is `players > four levers`. The exact objective and runtime values are needed before changing that condition. Likewise, blindly restoring Joker arrays on Leave/Back could duplicate items or overwrite a legitimate game transition.
